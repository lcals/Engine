# 首个游戏

## 玩法定位

首个游戏是一款参考《兽人必须死》的割草射击游戏。不同类型的大量敌人持续来袭，围攻并攻击玩家；玩家通过射击消灭敌人，获得收益并升级，形成持续迎敌、击杀、收益、升级的核心循环。

当前定位尚未确定防守基地、陷阱、自动攻击、随机升级选项或 Boss 等规则；这些不能因为参考作品或“割草”分类就视为既定需求。

## 当前工作范围

本页用首个游戏的需求识别引擎技术缺口。当前工作是补齐通用能力，并在 `projects/showcase` 中建立最小、可重复的验证场景；实际游戏的敌人决策、生命与伤害、击杀奖励、波次、升级和对局流程留在游戏项目。

**先补齐并验证主要技术缺口，确认没有影响目标玩法的大缺口后，才启动真正的项目原型。** 当前仍处于引擎技术准备阶段，不同时展开游戏业务。

showcase 可以提供操作按钮、查询结果高亮、计数和重置，用来观察技术是否正确。已有靶场的命中计数属于验证反馈，不据此继续扩展完整战斗业务。范例沿用公开范例模型；私有资源、购买内容和项目特定规则保持项目隔离。每项新增工作先说明缺少的通用能力及范例验收，再决定实现所属模块。

## 脚本与原生职责

**脚本层保持轻量，不承载重逻辑。** 通用高频能力由引擎核心或对应运行时功能插件执行；真实游戏的高频业务也可放在项目自有 C++ 模块中。是否采用 C++ 与是否属于通用引擎能力是两个独立判断，不能将游戏业务改名为通用战斗插件后加入范例。

| 层级 | 职责 |
| --- | --- |
| 引擎核心 | 输入与坐标转换、场景与资源、物理查询、导航基础、动画、渲染、时间与 KV 等通用能力 |
| 可选运行时功能插件 | 按既有架构组合通用能力；具体插件职责按当前技术缺口评审，不预设一个包揽游戏业务的战斗插件 |
| showcase 脚本 | 配置技术试件、提交操作、展示查询结果与状态、重置和退出；不演进成真实游戏的业务实现 |
| 真实游戏项目 | 定义敌人、武器、伤害、收益和对局规则；高频执行按需放项目自有原生模块，TS 负责配置、低频编排及 UI MVC |
| 编辑器与离线工具 | 制作、导入和校验资源与配置，构建运行数据，通过 MCP 组织验证流程 |

跨脚本边界按需要提交批次、返回结果批次或状态摘要；避免每个对象、每个组件每帧来回调用绑定，也不逐帧拷贝整个模拟世界。批处理接口围绕具体模块需求设计，不提前建立通用 Manager 或业务框架。

保存哪些游戏字段、何时保存、版本及迁移规则由游戏项目决定。小规模进度的低频 JSON 序列化属于项目脚本职责；大块快照由对应原生模块整理，避免脚本逐对象读取整个世界。

### 待补的通用技术

P0 为紧接当前射击查询的技术缺口，P1 为后续候选，条件项按实际使用需要评审；它们不是游戏业务的实现顺序。

| 优先级 | 技术缺口 | 当前边界与需要补齐的内容 | 所属层级 |
| --- | --- | --- | --- |
| P0 | 角色形体的命中查询 | 现有最近射线／球扫只覆盖 Collider，不覆盖 CharacterMotor 的 CharacterVirtual；需要明确统一查询、对象身份、自身过滤与帧内同步契约 | 核心物理与角色能力、对应脚本绑定 |
| P0 | 导航路径跟随 | 已有完整可达路径查询，缺少原生路径推进、目标变更／取消、到达和不可达状态，以及导航更新后的路径处理 | 导航能力与按架构评审确定的运行时功能插件 |
| P1 | 范围重叠查询 | 扫掠不能替代静态范围查询；需要重叠结果、对象去重、类别过滤与生命周期校验。Trigger 进入／离开事件须另行定义，GetImpacts 不承担该职责 | 核心物理与对应绑定 |
| P1 | 多代理避让与更新预算 | 路径跟随完成后再评估群体避让、共享路径、低频重寻路与错峰更新；优先复用已选 Recast／Detour 的上游能力 | 导航与相关运行时功能插件 |
| P1 | 模拟暂停与时间控制 | TS 只有 Time.deltaTime；跳过 Gameplay.Update 不会停止独立物理。需要明确模拟暂停、时间倍率，以及继续响应的输入、UI 和显示时间 | 核心提供机制，宿主与调用方选择策略 |
| P1 | 动画事件与分层 | 已有两动作过渡，缺少动作事件、分层与叠加；需要时间推进、过渡、循环与重载下明确的事件语义 | 动画能力与对应绑定 |
| P1 | 跨骨架动作复用 | 当前要求完整关节名称与层级匹配，直接使用源局部 TRS；语义映射、参考姿态和比例补偿、运行时重定向仍未实现 | 编辑器准备适配数据，运行时动画执行；见[角色制作规划](editor/character-production.md) |
| 条件项 | 对象批量操作与复用 | 已有节点创建／销毁和模型实例化；按真实调用量决定批量接口及复用能力，明确复位、引用失效和资源清理，不先建立敌人或武器对象池 | 对应场景、资源或运行时功能插件 |
| 条件项 | 大量对象渲染与动画预算 | 共享几何与 GPU 蒙皮已有实现，但绘制、动画采样和蒙皮仍逐实例推进；根据同负载实测决定批绘制、剔除、LOD 与更新分级 | 当前获准优化的渲染、动画及相关模块 |
| 条件项 | 文件与大块快照 | 字符串 KV 已实现，通用脚本文件接口和大块世界快照尚未实现；是否补齐取决于明确需求 | 对应核心能力与绑定，保存内容由调用方决定 |

TS Node 已有只读 `id` / `sceneId`，最近命中直接返回节点身份；`Physics.IsHitValid` 校验场景、节点和 Collider 实例。它不重算历史命中，也不代表调用方的业务对象复用代际或伤害事件仍有效。

当前同一节点不能同时启用 CharacterMotor 与 Collider / RigidBody，不能通过在 Motor 节点上补一个 Collider 绕过角色查询缺口。下一步先在类图中明确角色形体的查询与身份契约、所有权及同步顺序，再实现通用能力。

模型实例化只负责模型层级和表现资源。正式 Prefab、批量构建或复用契约随实际技术需求单独评审，不为靶场预先增加包含血量、武器和行为的单位工厂。

持久化已提供类似 [Unity PlayerPrefs](https://docs.unity.cn/6000.2/Documentation/ScriptReference/PlayerPrefs.html) 的轻量 KV 使用方式：Storage 按 key 获取、设置、判断存在、删除，以及显式保存并报告失败；缺少 key 与读取失败通过 `lastError` 区分。少量金币、解锁、设置可序列化为字符串，结构化进度由脚本转换为 JSON；本引擎使用自己的文件后端，接口与限制见 [KV 类图](runtime/class-diagrams/key-value-store.md)。

原生负责应用数据隔离、读写边界与写入后替换，数据落在持久目录的独立用户数据区域。若后续暴露文件接口，使用该区域下的相对路径；二进制大快照由原生模块读写。游戏字段含义、版本和迁移保持项目职责，本项不要求新增专用游戏存档系统，也不涉及加密、防作弊或云存档。

### 实际游戏项目的业务需求

以下内容仅记录真正游戏的需求背景，不属于 showcase 当前实现计划，也不因为引擎尚未提供这些业务就将它们列为通用技术缺口。具体规则与高频执行留在游戏项目，TS 保持低频编排与 UI 职责。

| 范围 | 尚需定义与实现 |
| --- | --- |
| 对局状态 | 准备、战斗、失败或完成、重开与退出；进入和退出时资源及单位配对清理 |
| 玩家与武器 | 玩家生命、射击方向、射速、弹道与命中规则；是否有弹药、装填、不同武器由策划确定 |
| 敌人 | 不同类型的属性、移动、追击、攻击、受击与死亡；出生点、数量上限、离场和回收规则 |
| 来袭节奏 | 持续生成或分波、每阶段敌人组合、难度增长、生成预算与停止条件 |
| 击杀与收益 | 击杀归属、奖励数值、收益累计；奖励直接到账还是生成拾取物仍需确定 |
| 升级 | 升级条件、收益消耗或经验阈值、可升级项、数值应用和上限；随机选项不是当前已确定规则 |
| HUD 与结算 | 血量、武器状态、收益、升级入口、失败或完成界面及重开按钮 |
| 项目数据 | 角色、敌人、武器、关卡与升级配置的校验及编译；原生模块读取已校验运行数据，脚本选择配置并提交批量请求 |

## 大量敌人运行的实际差距

大量敌人围攻用于验证单位能否同时更新、移动、攻击、播放动作和渲染。静态摆放数量、建筑碎块数量或某个第三方库的容量上限，不能代替这一目标。

- **渲染查找与提交。** [资源准备](../src/engine/runtime/render/render_scene_resources.cpp)和[绘制](../src/engine/runtime/render/render_scene.cpp)逐节点在线性 Mesh 容器中查找；当实例数量随节点数量增长时存在 O(N²) 查找路径。普通网格尚无 instancing；Camera 的可见名单是显式隐藏控制，不是自动视锥剔除。上述为源码结构判断，实际耗时尚需对应场景测量。
- **动画与蒙皮。** 不可变骨架和动作编译物已共享，但 CPU 仍逐实例采样、计算骨矩阵；每个蒙皮实例拥有独立 palette 和输出顶点流，分别提交 compute。尚无动画更新分级和群体蒙皮批处理。
- **导航与物理。** 当前导航同步构建、替换和查询，没有群体代理与避让。不能默认每名敌人每帧独立寻路，也不能默认所有敌人与弹体都使用完整动态刚体；碰撞精度与近远更新策略要由真实玩法和预算决定。
- **破坏后的通行。** 已有局部导航替换能力，但挖地、建筑倒塌、残骸移动后的更新时机、重寻路和拥堵处理仍需调用方组织；没有自动动态残骸导航。
- **特效与声音。** 已接入真实播放能力，仍需定义同时在播上限、远近优先级、过载处理和复用策略。Effekseer 的固定容量不能解读成可支持同数量敌人。

[现有性能基线](runtime/performance.md)来自建筑破坏场景，其中 503 个物理 body 不代表 503 名具有追击、攻击和动画的敌人。现有动画与 GPU 蒙皮检查覆盖功能正确性，尚未给出大量战斗单位的容量结论；Windows、M1 Max 和 Android 设备分别需要自己的目标预算。

## 技术补齐顺序与范例验收

以下为待实施的技术计划。每次只推进选定模块及其必要链路，showcase 提供最少的操作脚本和可观察结果。

| 顺序 | 引擎能力 | 最小验证场景 | 验收重点 |
| --- | --- | --- | --- |
| 1 | 角色参与最近命中查询 | 一个可移动胶囊、一面墙，操作射线和球扫并高亮结果 | 与 Collider 比较最近命中；移动后结果符合约定帧序；自身过滤、遮挡、组件重建与切场景后的身份失效 |
| 2 | 导航路径跟随 | 向一个胶囊提交目标点，观察其绕障到达 | 目标变更、取消、到达、不可达和局部导航更新后的路径处理；退出后停止移动；先完成单代理 |
| 3 | 通用范围查询 | 手动移动一个球形区域，高亮重叠对象 | 初始重叠、边界、对象去重、类别过滤和删除清理；范围查询与持续接触事件分别明确契约 |
| 后续按缺口选择 | 时间控制、动画事件／分层、多代理避让及批量能力 | 暂停模拟但保留 UI 操作；播放动作观察事件；多胶囊目标移动等独立技术试件 | 对应能力的生命周期、确定性、事件清理和实际规模；不加入生命、伤害、奖励或对局规则 |

**下一步先补角色查询。** 现有靶场已验证普通 Collider，角色形体查询尚未覆盖，适合沿当前物理查询链路继续补齐。优先核对 Jolt 的 CharacterVirtual 与官方查询范例；后续导航复用已选 Recast／Detour 的路径与代理实现。新增公开契约先按[类图索引](class-diagrams/index.md)更新职责、所有权和接口供评审，不另建平行算法框架。

技术容量验证使用固定场景、随机种子与操作序列，复用 MCP 启停、同步、截图、日志和现有 Tracy 流程。记录活动对象数、查询或路径请求数、状态、帧时间分位数和内存；调用方只获取当前模块必要的摘要。其他模块热点先记录，扩展优化范围由用户确定，再根据同负载结果决定空间结构、批处理、LOD 或线程化。

## 进入项目原型的条件

重大缺口以首个游戏实际必需的通用能力为准。进入原型前，复核角色查询、导航与多对象移动、所需范围交互、动画与时间控制，以及目标规模和平台上的可用性，逐项记录“已验证、仍阻塞、可延后”及依据。

- 关键能力已有可调用接口，并通过 showcase 中对应的独立技术范例验证，不能只有依赖登记或静态推断。
- 所需能力组合后的生命周期、资源清理和规模基线可接受；目标数量或平台尚未明确、尚未验证的部分如实保留，不能提前宣称已达标。
- 仍需补的关键通用能力继续在引擎阶段完成。剩余内容为已明确可延后的细节或项目业务时，再启动真正游戏的原型开发。

真正游戏的视角、移动端操作、目标设备与活动数量、收益升级规则及局内／局外成长边界仍需在游戏项目确定。当前范例的镜头、即时命中与计数都是验证条件，不自动成为正式玩法约定。
