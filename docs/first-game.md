# 首个游戏

## 玩法定位

首个游戏是一款参考《兽人必须死》的割草射击游戏。不同类型的大量敌人持续来袭，围攻并攻击玩家；玩家通过射击消灭敌人，获得收益并升级，形成持续迎敌、击杀、收益、升级的核心循环。

当前定位尚未确定防守基地、陷阱、自动攻击、随机升级选项或 Boss 等规则；这些不能因为参考作品或“割草”分类就视为既定需求。

## 脚本与原生职责

**脚本层保持轻量，不承载重逻辑。** TypeScript 负责配置选择、对局阶段编排、低频业务请求、UI MVC 和结果展示。后续战斗能力按可选原生运行时插件组织，负责大量单位逐帧更新、寻路与避让、弹体模拟、空间查询、命中筛选、伤害结算和生命周期批处理，复用核心已有能力。

| 层级 | 职责 |
| --- | --- |
| 引擎核心 | 输入与坐标转换、场景与资源、物理查询、导航基础、动画、渲染、通用时间与文件 / KV 存取能力 |
| 原生运行时战斗插件 | 敌群与弹体的批量模拟、目标筛选、攻击与伤害结算、单位生成回收、战斗数据及预算管理；消费项目明确提交的规则与配置 |
| 项目 TypeScript | 选择关卡、敌人和武器配置，切换对局阶段，提出生成、开火或升级请求，订阅汇总结果，更新 HUD 和结算界面 |
| 编辑器与离线工具 | 制作、导入和校验资源与配置，构建运行数据，通过 MCP 组织 AI 制作和验证流程 |

跨脚本边界按批次提交请求、返回事件批次或状态摘要；避免每个敌人、每颗子弹、每个组件每帧来回调用绑定。脚本也不逐帧拷贝整个战斗世界。伤害公式、敌人差异与升级规则由项目定义，可用配置交给原生模块求值；具体游戏规则不写入通用引擎核心。

保存哪些字段、何时保存、数据版本及迁移规则由项目脚本决定。小规模进度的低频 JSON 序列化属于脚本职责；大量单位或世界状态的快照由原生模块整理，避免脚本逐对象读取整个世界。

## 当前评估

本节描述当前代码能力与玩法缺口；平台验证范围集中在根 README。现有能力可以复用来制作战斗原型，但尚未组成完整的割草射击游戏框架，也没有大量敌人同时模拟、寻路、播放动作和渲染的性能结论。依赖已接入、演示场景已运行、目标能力已规划，三者分别记录。

当前已完成 `projects/showcase` 的简单射击靶场，菜单第九项 `Shooting range` 可进入。它验证了移动、瞄准、射线／球扫、墙体遮挡、命中反馈、计分、重置和菜单往返。下一阶段从这个范例扩展敌人战斗，继续使用原有范例模型；项目规则、私有资源和购买内容不混入其他项目。通用插件通过项目配置复用。

### 缺少的通用能力与原生游戏模块

优先级含义：P0 用于打通射击、受伤、击杀和收益的最小闭环；P1 用于达到大量敌人运行及完整对局要求；条件项随明确玩法启用。

| 优先级 | 缺口 | 当前限制与需要完成的内容 | 所属层级 |
| --- | --- | --- | --- |
| P0 | 原生单位生命周期 | 目前有模型实例化，但没有敌人生成、复位、死亡回收的完整原生链路。需要独立单位身份与复用代际、受击形体到单位的映射，以及表现和碰撞的配对启停 | 原生运行时战斗插件 |
| P0 | 战斗结算与基础追击 | 尚无玩家和敌人生命、攻击冷却、伤害、受击、死亡、击杀归属与奖励批次。需复用现有导航与 Motor 实现单个敌人的路径跟随、接近攻击和不可达处理；高频推进留在原生，脚本消费摘要 | 原生运行时战斗插件；规则由项目配置 |
| P1 | 实体弹体批处理 | 现有火箭为 TS 演示池；采用飞行弹体时需要原生发射、分段扫掠、命中或超时回收及预算。首版即时射线武器直接消费命中结果，不以实体弹体系统为前置条件 | 原生运行时战斗插件 |
| P1 | 接触、范围与区域交互 | 当前 `GetImpacts` 排除 Sensor，不能作为触发器进入/离开或持续接触事件。范围攻击、拾取和接触攻击需要可靠的查询或重叠事件；不得靠每帧脚本两两比较单位 | 通用查询归核心；范围筛选与攻击规则归原生游戏模块 |
| P1 | 怪群追击与避让 | 有单次同步路径查询，没有代理跟随、局部避让、共享路径和更新预算。需要低频重寻路、错峰更新、拥堵处理及目标不可达策略 | 原生导航扩展 / 游戏模块 |
| P1 | 对局暂停与时间控制 | TS 只有 `Time.deltaTime`；跳过 Gameplay.Update 不会停止独立推进的物理。需要明确模拟暂停、时间倍率，以及暂停时继续处理的 UI、输入和显示时间 | 核心提供时间能力，宿主 / 对局调用方选择策略 |
| P1 | 攻击动作衔接 | 已有两动作过渡；缺动作事件、上半身与下半身分层、瞄准叠加等能力。需要处理攻击生效、发射、受击打断与动作结束；首版可由原生战斗时间线明确驱动 | 动画能力及原生游戏模块；具体状态规则归项目 |
| P1 | 跨骨架动作复用 | 当前要求完整关节名称与层级匹配，直接使用源局部 TRS；语义映射、参考姿态和比例补偿、运行时重定向仍未实现 | 编辑器准备适配数据，运行时动画执行；见[角色制作规划](editor/character-production.md) |
| P1 | 大量单位渲染与动画预算 | 共享几何与 GPU 蒙皮已有实现，但普通 Mesh 仍逐实例提交；动画采样和蒙皮也逐角色执行。需要处理已知查找复杂度，并按真实怪群负载决定批绘制、剔除、LOD 与更新分级 | 渲染、动画及相关原生模块，按实测逐项推进 |
| 条件项 | 局外进度与大块快照 | 通用字符串 KV 已实现；本游戏保存哪些收益、解锁和升级数据及如何迁移尚待业务定义。通用脚本文件接口和大块世界快照仍未实现 | 项目脚本组织低频进度并调用 KV；批量快照归原生游戏模块 |

TS Node 已提供只读 `id` / `sceneId`，最近命中查询直接返回 Node 身份包装；`Physics.IsHitValid` 校验场景、节点和 Collider 实例。后续原生单位模块应登记节点与单位的映射，不依靠名称或场景遍历关联战斗对象。业务阵营、伤害过滤与通用 Trigger 事件仍待对应模块实现。

当前射线／球扫查询只覆盖 `Collider`，不包含 `CharacterMotor` 使用的 `CharacterVirtual`；同一节点也不能同时启用 Motor 与 Collider / RigidBody。接入敌人前，先在类图中明确运动形体、受击形体、更新顺序和单位映射，不能把“能移动”视为“能被射击命中”。`IsHitValid` 不重算历史命中，同一个 Collider 被单位池复用时也不会自动改变身份；攻击有效期、单位复用代际、重复伤害与重复奖励由战斗插件校验。

模型实例化只负责模型层级和表现资源，不能当作包含血量、武器、行为与完整碰撞配置的玩法 Prefab。首版可由原生单位工厂消费项目配置组合现有组件；是否扩展正式 Prefab 资源契约，随实际复用需求单独评审。

持久化已提供类似 [Unity PlayerPrefs](https://docs.unity.cn/6000.2/Documentation/ScriptReference/PlayerPrefs.html) 的轻量 KV 使用方式：Storage 按 key 获取、设置、判断存在、删除，以及显式保存并报告失败；缺少 key 与读取失败通过 `lastError` 区分。少量金币、解锁、设置可序列化为字符串，结构化进度由脚本转换为 JSON；本引擎使用自己的文件后端，接口与限制见 [KV 类图](runtime/class-diagrams/key-value-store.md)。

原生负责应用数据隔离、读写边界与写入后替换，数据落在持久目录的独立用户数据区域。若后续暴露文件接口，使用该区域下的相对路径；二进制大快照由原生模块读写。游戏字段含义、版本和迁移保持项目职责，本项不要求新增专用游戏存档系统，也不涉及加密、防作弊或云存档。

## 大量敌人运行的实际差距

大量敌人围攻用于验证单位能否同时更新、移动、攻击、播放动作和渲染。静态摆放数量、建筑碎块数量或某个第三方库的容量上限，不能代替这一目标。

- **渲染查找与提交。** [资源准备](../src/engine/runtime/render/render_scene_resources.cpp)和[绘制](../src/engine/runtime/render/render_scene.cpp)逐节点在线性 Mesh 容器中查找；当实例数量随节点数量增长时存在 O(N²) 查找路径。普通网格尚无 instancing；Camera 的可见名单是显式隐藏控制，不是自动视锥剔除。上述为源码结构判断，实际耗时尚需对应场景测量。
- **动画与蒙皮。** 不可变骨架和动作编译物已共享，但 CPU 仍逐实例采样、计算骨矩阵；每个蒙皮实例拥有独立 palette 和输出顶点流，分别提交 compute。尚无动画更新分级和群体蒙皮批处理。
- **导航与物理。** 当前导航同步构建、替换和查询，没有群体代理与避让。不能默认每名敌人每帧独立寻路，也不能默认所有敌人与弹体都使用完整动态刚体；碰撞精度与近远更新策略要由真实玩法和预算决定。
- **破坏后的通行。** 已有局部导航替换能力，但挖地、建筑倒塌、残骸移动后的更新时机、重寻路和拥堵处理仍需调用方组织；没有自动动态残骸导航。
- **特效与声音。** 已接入真实播放能力，仍需定义同时在播上限、远近优先级、过载处理和复用策略。Effekseer 的固定容量不能解读成可支持同数量敌人。

[现有性能基线](runtime/performance.md)来自建筑破坏场景，其中 503 个物理 body 不代表 503 名具有追击、攻击和动画的敌人。现有动画与 GPU 蒙皮检查覆盖功能正确性，尚未给出大量战斗单位的容量结论；Windows、M1 Max 和 Android 设备分别需要自己的目标预算。

## 实现顺序与验收

### 下一阶段：一个敌人的完整战斗

建议继续在 showcase 射击范例中推进，首版使用一名玩家、一类敌人和一种即时命中武器。现有靶场保留为坐标与查询回归用例。以下是下一阶段的实现计划，不代表已经完成。

1. **先明确受击与单位契约。** 类图定义原生战斗插件的最小职责、组件与系统关系、单位身份、受击形体和资源所有权；接口只覆盖配置、生成／回收、玩家意图、状态摘要与事件批次。血量、射速、伤害、攻击距离和奖励数值来自项目配置。
2. **让一个敌人追击并攻击。** 复用导航路径查询与 CharacterMotor，原生推进路径跟随、低频重寻路、攻击距离和冷却。明确绕障、不可达、停止与玩家死亡后的行为；敌人不复用玩家控制器的输入和相机。
3. **把命中接到伤害与死亡。** 将最近命中关联到战斗单位，执行双方生命、攻击冷却、伤害、死亡、击杀归属和一次性奖励。保留墙体遮挡；射击与受击形体同步采用明确的帧内顺序，避免使用上一帧姿态造成额外延迟。
4. **补齐可重开的验证场景。** TS 选择配置、提交玩家操作、更新血量／击杀／收益 HUD，并组织开始、失败与重开；原生插件负责停止模拟和清理单位。奖励先输出已确认的结算结果，到账或拾取表现由项目规则决定。

本阶段验收：敌人能绕过障碍接近玩家，在攻击距离内按冷却扣血；墙后不能直接命中或隔墙伤害；玩家射击能扣除敌人生命并触发一次死亡与奖励；失效攻击不能伤害复用后的新单位；玩家死亡后停止战斗，重开恢复初始状态；退出后没有残留移动、碰撞、动作、特效或事件订阅。先用单个敌人验收，再用少量同类敌人核对状态相互独立。

### 随后推进

| 顺序 | 用户可见结果 | 验收重点 |
| --- | --- | --- |
| 2. 完整对局 | 多个敌人持续来袭，击杀获得收益、升级影响战斗，失败或完成后重开 | 原生批量生成与复用；奖励只结算一次；升级影响后续攻击；暂停覆盖物理与战斗，UI 继续响应 |
| 3. 怪群规模 | 同一玩法按配置逐档增加活动敌人；选择实体弹道时再加入原生弹体批处理 | 固定场景与种子，统计帧时间分位数、脚本调用、原生战斗、导航、物理、动画、渲染及内存；所有可见单位真实参与移动和攻击 |
| 4. 内容与表现 | 更多敌人与武器、攻击／受击动作、特效音效及资源制作流程 | 按实际素材需要补动画分层、动作事件或重定向；项目参数驱动资源，不写具体模型特例 |

性能优化以当前开发模块及必要链路为边界；其他模块热点先记录，扩展范围由用户确定。先取得同负载基线，再决定批处理、空间结构、LOD 或线程化，不以关闭 AI、攻击或动画换取数量结果。局外成长明确后再使用已有 KV 保存项目进度。

AI 自动验证复用现有 MCP 启停、资源同步、截图和日志。项目还需提供固定随机种子、明确的可重复开局与操作序列，以及活动敌人、弹体、击杀、收益和对局阶段等状态摘要；这些入口服务本游戏，不要求通用任意脚本执行框架。

当前范例已有第三／第一人称切换与中央准星即时命中，可直接作为下一阶段的验证操作。最终游戏的视角、移动端操作、目标设备与活动数量、收益升级规则及局内／局外成长边界仍需确定；范例参数不自动成为正式玩法约定。
